# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A household expense tracker: a Streamlit UI talks to a FastAPI backend over HTTP, which persists to a Postgres star schema, and an ETL step exports that schema to a Tableau Cloud datasource. Everything runs through `docker-compose.yml` (db, backend, frontend, pgadmin) with `.env` at the repo root supplying every credential.

## Product intent

Two people — the owner and his wife — each log their own expenditures, and the owner analyses them: the current month first, and increasingly month-over-month as history accumulates. Analytics is the point of the project, not a bolt-on, so weigh changes against whether they make the data easier to analyse over time.

Tableau is deliberate scope. The dev site and the embedded dashboard exist because learning Tableau is one of the project's goals, and it stays the long-term home for analysis. The Analytics page's **Overview** tab (Altair charts over `/analytics/shared`) is an interim in-app view the owner asked for — shared expenses, this month against earlier months — and it lives next to the **Tableau** tab rather than replacing it. Don't grow the Overview into a substitute for Tableau or propose dropping the embed.

This is a learning project. The owner wants to be walked through changes and understand the trade-offs, not handed finished features — default to explaining and proposing sequenced steps, and check before implementing.

**Shared expenses are split by an income-derived proportion, not 50/50.** `FactExpenditure.user_id` is who *paid*; who *bears* the cost lives in `fact_expenditure_split` (one row per person per expense, `share_pct` and `share_amount` snapshotted at write time from `household_setting`). Per-person spending must be computed from the split table, not from `FactExpenditure.user_id`. In Tableau, per-person analysis belongs on the `allocations` datasource; the older `expenditures` datasource still attributes 100% of a shared cost to the payer. The design work lives in the gitignored `notes/` folder, which also holds the project review and roadmap; read `notes/README.md` before proposing schema changes.

## Commands

Docker is the primary workflow — both app containers bind-mount their source, so code edits hot-reload without a rebuild.

```powershell
docker compose up --build          # full stack: API :8000, UI :8501, pgAdmin :5050, Postgres on $DB_PORT
docker compose up -d db            # database only (e.g. to run backend locally)
docker compose logs -f backend     # tail one service
docker compose down -v             # DESTROY the postgres_data volume (Alembic rebuilds it on next start)
docker compose build --no-cache backend   # needed after editing pyproject.toml/poetry.lock
```

Running a service outside Docker (from `backend/` or `frontend/`, each has its own Poetry project and `.venv`):

```powershell
poetry install
poetry run uvicorn main:app --reload      # backend/ — imports are flat ("import models"), so cwd MUST be backend/
poetry run streamlit run Home.py          # frontend/
```

Note that outside Docker the backend reads `DB_HOST`/`DB_PORT` straight from `.env`, which currently holds the Compose values (`db` / `5432`) — running the API on the host therefore requires setting `DB_HOST=localhost` first. Inside Docker, `docker-compose.yml` overrides them to `db:5432` regardless.

Utility scripts:

```powershell
poetry run python init_db.py              # backend/ — CREATE DATABASE if absent; tables come from Alembic
poetry run python -m etl.main             # backend/ — run the Tableau ETL directly (same code path as POST /refresh)
poetry run python seed.py                 # backend/ — seed months of demo history (--months, --random-seed, --append)
docker compose exec backend python reset_password.py someone@example.com   # set a password by hand (prompts twice)
```

Migrations run inside the backend container, where `DB_HOST=db` resolves:

```powershell
docker compose exec backend alembic current                      # which revision the DB is on
docker compose exec backend alembic history                      # the revision chain
docker compose exec backend alembic revision --autogenerate -m "what changed"
docker compose exec backend alembic upgrade head                 # apply
docker compose exec backend alembic downgrade -1                 # step back one
```

Tests (pytest, in `backend/tests/`) run inside the backend container:

```powershell
docker compose exec backend pytest                                   # whole suite
docker compose exec backend pytest tests/test_split_logic.py -v      # one file
```

Frontend tests (pytest, in `frontend/tests/`) need no database or API: pure helpers such as `frontend/money.py` (`parse_brl` / `format_brl`: every amount the UI reads or shows goes through them, as Decimal) and `streamlit.testing.v1.AppTest` page smoke tests. Run them on the host with `cd frontend && poetry install --with dev && poetry run pytest`; CI runs them as the `frontend-tests` job.

API tests hit a real Postgres, never SQLite. `tests/conftest.py` points `DB_NAME` at `<DB_NAME>_test` (or `$TEST_DB_NAME`) before anything imports `database`, drops and recreates that database, migrates it with `alembic upgrade head`, truncates every table after each API test, and drops the database at the end. It refuses to run against a name not ending in `_test`. GitHub Actions (`.github/workflows/ci.yml`) runs the same suite against a Postgres service container on every push and PR to `develop`/`main`. Every PR should add tests for what it changes.

There is no linter or formatter configured. Do not invent commands for them.

## Architecture

**Configuration.** Every backend setting goes through `backend/config.py`: a pydantic-settings `Settings` built once at import (`from config import settings`), reading environment variables first and then the repo-root `.env`. Required values (DB_*, `SECRET_KEY`) fail at startup with the variable named; Tableau credentials are optional until `settings.require_tableau()` runs at publish time, and SMTP credentials until `settings.require_email()` runs when sending with `EMAIL_BACKEND=smtp`, so tests and CI need neither. Don't add new `os.getenv` calls — add a field to `Settings` and a line to `.env.example`. The ETL reuses `database.engine` rather than building its own connection. The frontend's one setting, `API_URL`, is read in `frontend/config.py` and imported by every page as `API_BASE_URL`.

**Look and feel.** The app is called **Home Finances**. Its theme lives in `frontend/.streamlit/config.toml` (Roboto, brand green `#1f6f5c`, light base; read only at Streamlit startup, so `docker compose restart frontend` after editing it), and every page starts with `ui.setup(<page>)` then `ui.page_header(title, purpose)` from `frontend/ui.py`, which also provides `ui.lede()` (the green "what this is for" box opening a section) and `ui.callout()` (lead with the answer, e.g. who owes whom). Every colour has one job: green = household and actions, slate = money owed, orange ▲ = spent more, blue ▼ = spent less. Streamlit's own red/green slots are remapped to that orange/blue so `st.metric` deltas (`delta_color="inverse"` for spending) and `st.error`/`st.success` stay colour-blind safe; never introduce red/green for good/bad, and always pair colour with an arrow or sign. Charts use the same palette (`analytics_charts.py`). The CSS in `ui.py` targets only our own `hf-` classes, never Streamlit internals, so upgrades don't break it.

**Request path.** Streamlit pages are pure HTTP clients — they hold no DB connection. `frontend/Home.py` posts to `/token`, stashes the JWT in `st.session_state["access_token"]`, and every page under `frontend/pages/` re-checks that key and calls `st.stop()` if missing. `API_BASE_URL` comes from `frontend/config.py`, which reads the `API_URL` env var (`http://backend:8000` in compose, `http://localhost:8000` otherwise).

**Auth.** `backend/auth.py` does bcrypt hashing and HS256 JWT minting; `get_current_user` in `backend/main.py` decodes `sub` (the email) and re-fetches `DimUser`. `SECRET_KEY` is required (startup fails without it), and tokens expire after `ACCESS_TOKEN_EXPIRE_MINUTES` (default 30) — an expired token surfaces in the UI as a 401 that the pages translate to "Session Expired".

**Every route except signup, login and password reset requires a token.** `POST /users/`, `POST /token`, `POST /password-reset/request` and `POST /password-reset/confirm` are public; everything else depends on `get_current_user`, either as a parameter (when the handler needs the user) or via `dependencies=[Depends(get_current_user)]`. `tests/test_auth.py` keeps `PROTECTED_ROUTES` (each must reject a missing or invalid token) and `PUBLIC_ROUTES`, and `test_every_route_is_classified` fails until a new route is added to one of them.

**Password reset.** `POST /password-reset/request {email}` always answers 202 with the same body, so it never reveals whether an account exists. For a real account (email matched case-insensitively) it marks that user's earlier unused tokens used, stores a new row in `password_reset_token` — only the SHA-256 hex of a `secrets.token_urlsafe(32)` token (`auth.hash_reset_token`), never the token itself — and emails `{FRONTEND_BASE_URL}/?reset_token=<raw>` as a `BackgroundTasks` job. It sends nothing once the user has 3 tokens created in the last hour. `POST /password-reset/confirm {token, new_password}` locks the matching unused, unexpired row (`FOR UPDATE`), sets the new bcrypt hash and marks the token used in one commit; any failure is a 400 "This reset link is invalid or has expired.", and a password under 8 characters is a 422. Existing JWTs stay valid until they expire. `frontend/Home.py` shows a "Set a new password" form when the URL carries `reset_token`, and a "Forgot password?" expander under the login form. Email goes through `backend/email_sender.py`: the `get_email_sender` dependency returns `ConsoleSender` (prints the message, the default, used in dev/tests/CI) or `SmtpSender` (STARTTLS, Gmail by default) per `EMAIL_BACKEND`; tests override the dependency with a recording fake, and `conftest.py` forces `EMAIL_BACKEND=console`. Settings: `EMAIL_BACKEND`, `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`, `EMAIL_FROM`, `FRONTEND_BASE_URL` (the LAN address, so links work from a phone), `PASSWORD_RESET_EXPIRE_MINUTES` (default 30). `backend/reset_password.py <email>` is the no-email fallback: it prompts for the password, and its `set_password()` is what the tests call.

**Hardening for LAN use.** The app is meant to be opened from other devices on the home network, so a signed-up account must not be able to harm the household. `POST /users/` checks `settings.signup_allowed(email)`: `ALLOWED_SIGNUP_EMAILS` (comma-separated, lowercased into a set) restricts signup and returns 403 "Sign-up is restricted on this installation" for anyone else; empty means signup is open, which is what tests and CI rely on (`conftest.py` forces it empty). `DELETE /users/{id}` only deletes the caller's own account (403 otherwise; the FK-violation 400 still applies), and Settings offers only "Delete my account". `GET /users/` still lists every account's name and email to any logged-in user — Settings uses it for the Household list; with the allowlist set, every account is a household member anyway. Don't log emails or passwords at login.

**Ownership model.** `POST /expenditures/` deliberately strips `user_id` from the request body (`model_dump(exclude={"user_id"})`) and substitutes `current_user.user_id` — the frontend still sends a dummy `"user_id": 0`. Reads and deletes go through `visible_to(user)` in `main.py`: the user paid it, **or** holds a split row for it. So a shared expense is visible and deletable by both household members, and an account outside the household sees none of the household's expenses. Use `visible_to` for any new expenditure endpoint.

**"Shared" is derived, not stored.** `FactExpenditure.has_other_share` (a `column_property` in `models.py`) is true when someone other than the payer holds a split row; `/summary/`, `ExpenditureRead.is_shared` and the ETL's `is_shared` column all read it. The request field `is_shared` on `POST /expenditures/` now only means "split this by the household ratio". There is no `is_shared` column: migration `bc61f597d8fe` dropped it (its downgrade rebuilds the column from the split rows, covered by `tests/test_migrations.py`), and `POST /expenditures/` excludes the field from the row it writes.

**Star schema.** `backend/models.py` defines `DimUser`, `DimCategory` (unique on primary+sub), `DimPaymentMethod` (unique on method+institution), `DimPet` (unique name), and `FactExpenditure`. `schemas.py` mirrors them for Pydantic; `ExpenditureRead` nests the dimension objects (`pet` may be null), which is why the read query uses `joinedload` and why the Tracker page reads dotted columns like `category.primary_category` after `pd.json_normalize`.

**Pets.** `DimCategory.for_pets` marks categories whose expenses are for the pets; `FactExpenditure.pet_id` (nullable) says which one, and NULL on a `for_pets` category means all of them ("Both": one expense, never split per pet). `POST /expenditures/` rejects a `pet_id` on any other category or an unknown pet (400). `/pets/` has GET (with `expense_count`), POST, PATCH (rename) and DELETE (400 while in use). The Tracker shows a "Which pet?" radio (each pet plus Both) only for a `for_pets` category — required when there are two or more pets, implicit with one. Every expense datasource in the ETL carries `pet`: the name, `'Both'`, or NULL when the category isn't for pets, so Tableau sums cost per pet across categories.

**Splits and balances.** `POST /expenditures/` writes the expenditure and its split rows in one transaction through `ledger.add_expenditure` (which flushes but never commits, and is also what `seed.py` uses), splitting with the pure `split_logic.split_amount` (last share absorbs the rounding remainder, so parts always sum to the price). An optional `shares` list on the request overrides the household ratio for that one expense (`split_source="manual"`): it must sum to 1, name each person once, only accompany `is_shared` true, and name only household members (a 400 otherwise). A shared expense whose payer has no household share is a 400 too (`ledger.PayerNotInHousehold`), because the ratio would hand all of it to other people. The Tracker exposes it as "Custom split for this expense". `GET /balances/?month=YYYY-MM` reports paid / borne / net per person and the settling transfers (pure `split_logic.settle`). It counts only expenses with a split row for someone other than the payer, so one person's personal spending never appears in the other's view; months are São Paulo calendar months.

**Joint accounts.** `DimPaymentMethod.is_joint` marks an account both people top up in advance (e.g. a shared Nubank debit card for groceries). An expense paid from it is still shared and split as usual, so every "borne"/"my share" figure counts it, but `/balances/` treats each person as having paid exactly their own share, so it nets to zero and never makes anyone owe. Flipping the flag re-reads past expenses on that method. The Tracker locks "Shared" on (with a note) for a joint method, Settings has a Joint tick box, the Analytics drill-down shows "Joint account" as the payer, and every expense datasource carries `paid_from_joint`. 

**Joint account pot.** `fact_joint_entry` records what goes into a joint account: `kind` 'deposit' (money in) or 'balance' (what the bank showed then: the starting balance, or a correction when unlogged spending made the app drift). Who deposited is deliberately not stored, and entries never touch `/balances/`. `GET /joint/status` returns, per joint method: `balance` = latest balance check + deposits after it − everything that method paid after it (without a check, counted from the first deposit; NULL until either exists), and this São Paulo month's pace: cumulative spend by day against the "usual" month, the average of up to the last 3 *full* months (a month counts only if the account was already tracked — first expense or entry — on its 1st; none yet means `usual_to_day` NULL, "not enough history"), and `runs_out_on` = today + balance ÷ this month's daily rate. Arithmetic lives in the pure `backend/joint_logic.py`. `/joint/entries` has POST, GET (newest first) and DELETE; all four routes are for household members only (403 otherwise), and entries need an `is_joint` method (400). The Tracker gets a **Joint account** tab (only when a joint method exists and you're in the household): three metrics, a cumulative chart (this month solid, usual dashed; `analytics_charts.joint_pace_chart`), a form for deposits/balance checks and recent entries; text and frames come from the pure `frontend/joint_shaping.py`.

**Settlements.** `fact_settlement` records money moved between members to square up (`/settlements/` POST, GET, DELETE; only the payer or payee may record or delete one). `/balances/` folds them in: net = paid − borne + settled_out − settled_in. A settlement's `period_month` (the month it squares up, set from the Tracker's selected period) is deliberately separate from `settled_at` (when the money moved), because October is usually paid back in November; month views filter on `period_month`, and a settlement with `period_month` NULL counts only towards the all-time balance. The ETL publishes them as the `settlements` datasource.

Keep arithmetic in `split_logic.py`, free of DB access, so it stays unit-testable.

**Monthly summary.** `GET /summary/?month=YYYY-MM` (defaults to the current São Paulo month) is from the logged-in user's point of view: their total borne (share of shared + personal) against the previous month, the household's shared total, and their spending by primary category and cost type. It deliberately never exposes the other person's personal spending; cross-person analysis belongs in Tableau. The Tracker page's "Monthly Overview" section drives both `/summary/` and `/balances/` from one period picker.

**Shared-expense analytics.** `GET /analytics/shared?month=YYYY-MM&months=N` (month defaults to the current São Paulo month; `months` 1–24, default 12, the window *ends* at `month`) feeds the in-app Analytics Overview. It returns `{month, months, is_partial, as_of_day, rows}`: `months` is the whole window oldest first (empty months have no rows, so clients zero-fill from it), and each row is one São Paulo month × primary/sub category × cost type with `household` (sum of full prices), `mine` (sum of the caller's `share_amount`), `count`, and `household_to_day` / `mine_to_day` — the same sums over days 1..`as_of_day` only. `as_of_day` is today's São Paulo day when `month` is the current month (`is_partial` true), else that month's length, so a month in progress can be compared with the same days of earlier months. `GET /analytics/shared/expenses?month=YYYY-MM&primary_category=...` lists the individual expenses behind it (newest first; price, my share and share_pct, payer name, payment method, installments, nature). Both use one privacy rule: the expense is shared (`has_other_share`) **and** the caller holds a split row for it or paid it (the same people `visible_to` admits) — the caller's split row is outer-joined to supply "mine", which is 0 for an expense the caller paid but split entirely onto the partner. Personal expenses (anyone's) never appear, and an account outside the household gets empty rows. Missing categories show as "Uncategorised"/"Unknown", as in `/summary/`. Money is serialised as decimal strings. The code is the last section of `main.py`; tests are in `tests/test_analytics.py`, which freezes "today" by monkeypatching `main.datetime`.

**Settings page.** `frontend/pages/3_Manage_Settings_.py`, in order: **Household** (every account with a share-% input, you first, 0% = not in the household; Save PUTs the non-zero shares; there is no add-a-person form, a partner signs up on Home and the allowlist admits them), **Categories** (with a Pets tick box for `for_pets`), **Payment methods** and **Pets** as `st.data_editor` tables (edit cells, type in the last row to add, select and Delete to remove, plus a read-only "Used by" column; payment methods have Credit and Joint tick boxes), **Publish to Tableau**, and a "Delete my account" expander. Nothing in a table is written until **Save changes**, which first lists the plan in sentences; `frontend/settings_logic.py`'s pure `plan_changes` diffs the table before and after into POST/PATCH/DELETE calls and blocks saving (with the reason) on blank required cells, duplicates or removing a row in use. Editor keys carry `settings_nonce`, bumped after a save so the tables reload. AppTest can't edit a `data_editor`, so `tests/test_settings_logic.py` covers the diff and `tests/test_settings_page.py` the rendering and the split.

**Analytics Overview page.** `frontend/pages/2_Analytics.py` has two tabs: **Overview** and **Tableau** (the unchanged embed, which renders even when logged out). The Overview fetches `/analytics/shared` for 12 months ending at the picked month and draws, for the chosen lens (Household / My share): KPIs (total with delta vs the previous month — same days while the month is in progress —, vs the average of the three previous full months, expense count, biggest category increase; `delta_color="inverse"` so spending up is red), a monthly trend (partial month faded and labelled "to date", never projected; dashed 3-month average once three full months of history exist), category bars with a previous-period tick plus a biggest-changes table, a category × month heatmap, a drill-down (sub-categories and the month's expenses from `/analytics/shared/expenses`) and fixed vs variable. All data shaping lives in the pure `frontend/analytics_shaping.py` (floats for Altair; every displayed amount goes through `format_brl`), the Altair specs in `frontend/analytics_charts.py`; the page only wires widgets to them. Tests: `tests/test_analytics_shaping.py` (shaping, text, chart specs build) and `tests/test_analytics_page.py` (AppTest with `requests.get` patched; it starts from `Home.py` and `switch_page`s so `st.page_link` resolves, and presets segmented controls through session state because AppTest 1.50 can't `set_value` them).

**ETL.** `POST /refresh` calls `etl.main.run_pipeline()` synchronously inside the request: SQL joins → pandas → `pantab` writes one Hyper file per datasource under `artifacts/` (relative to cwd, i.e. `backend/artifacts/` in the container) → `etl/tableau_manager.py` signs in with a Personal Access Token and publishes each with `Overwrite` into `settings.tableau_project_name` (`TABLEAU_PROJECT_NAME`, default `"Finance App 2026"`) — a wrong value silently publishes into another project, leaving the workbook stale. The Tableau datasource name comes from the file name:

- Every expense datasource (`expenditures`, `allocations`, `cashflow`) has `paid_from_joint`: true when the joint account paid, so `paid_by` is only who logged it.
- `expenditures` — one row per expense, `price` attributed to the payer. Kept unchanged so existing workbooks keep working.
- `allocations` — one row per person per expense from `fact_expenditure_split`: `borne_by`, `paid_by`, `share_pct`, `share_amount`, `split_source`, `month_start` (São Paulo), plus category/payment/installment columns. Per-person analysis should `SUM(share_amount)` here. `expense_total` repeats the full price on every row of an expense, so never sum it.
- `cashflow` — the allocation grain spread over installment billing months, built with `generate_series` in SQL: one row per person per expense per installment, with `billing_month`, `purchase_month`, `installment_number`, `total_installments` and `amount`. `SUM(amount)` by `billing_month` is what each month actually cost, card statements included. Each share is divided by the installment count, all but the last rounded *down* to the cent and the last taking the remainder, so parts sum exactly and never go negative. Expenses without installments appear once, in their own month.
- `settlements` — one row per payment between members: `settled_at`, `settled_month_start`, `period_month` (the month it squares up; NULL = all-time), `from_name`, `to_name`, `amount`, `note`, `recorded_by`. Kept out of the spending grain because it moves money rather than spending it.

- `joint_account` — one row per joint-account entry (`kind` deposit/balance, `amount`, `entry_at`, `entry_date`, `month_start`, method/institution, `note`). Its spending side is the expense datasources' `paid_from_joint` rows.

- `calendar` — one row per São Paulo day with no gaps (`date`, `week_start` (Monday), `iso_year`, `iso_week`, `month_start`, `month_number`, `month_name`, `quarter`, `year`, `day_of_month`, `weekday_number` (ISO, Monday = 1), `weekday_name`, `is_weekend`, `is_future`), from 1 January of the first expense's (or settlement's) year to 31 December of the later of this year and the last installment's billing year. Built by `generate_series` at publish time, not stored in Postgres. In Tableau it is the left side: relate `calendar.date` to `transaction_date` (on `expenditures`, `allocations`, `cashflow`) or `settled_date` (`settlements`), or `calendar.month_start` to `cashflow.billing_month`, so days without spending still appear (`ZN()` for zeros).

Every date column is published as TIMESTAMP (pinned with `pd.to_datetime`), so both sides of a relationship have the same type. A datasource with no rows is skipped rather than published empty; the calendar is never empty.

`generate_hyper_file` casts all-NULL *untyped* columns to text, because Hyper rejects a column whose type can't be inferred. Date columns that may be entirely NULL must be pinned with `pd.to_datetime` in their extract, or they publish as text and flip type on a later refresh, which breaks workbooks. The Analytics page's Tableau tab iframes a hardcoded Tableau Cloud URL. A publish failure re-raises so the endpoint returns 500.

## Schema changes

**Alembic owns the schema.** Migrations live in `backend/alembic/versions/`, and the backend container runs `alembic upgrade head` before starting uvicorn (the `command:` override on the `backend` service in `docker-compose.yml`), so a fresh volume migrates itself on `docker compose up`. There is no `create_all` call any more — do not add one back, or two systems create the same tables and `alembic_version` stops describing reality.

`alembic/env.py` sets `sqlalchemy.url` from `database.DATABASE_URL` rather than from `alembic.ini`, which keeps credentials out of a committed file; it imports `models` purely so `Base.metadata` is populated; and it sets `compare_type=True` so column type changes are detected at all.

To change the schema: edit `models.py`, autogenerate a revision, **read the generated file before running it**, then upgrade. Autogenerate is a diffing tool, not an oracle — it reads a rename as drop-then-add, and `default=` in `models.py` is a Python-side default that never reaches Postgres, so new columns arrive as NULL on existing rows unless the migration backfills them explicitly.

The first revision (`b24c43f3c0f3`, "baseline: existing schema") was **stamped, not executed**, on the existing database. It describes the pre-Alembic schema — including `price` as `Float`, which the next revision converts to `Numeric(10, 2)`. Because it never ran locally, bugs in it are invisible here. Validate any change to it by building a throwaway database from scratch:

```powershell
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "CREATE DATABASE fresh_check;"'
docker compose exec -e DB_NAME=fresh_check backend alembic upgrade head
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" --schema-only --no-owner fresh_check'
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "DROP DATABASE fresh_check;"'
```

The dumped schema must match the live database. The full procedure — including the review checklist for generated revisions and a `diff` that ignores `pg_dump`'s random `\restrict` keys — is the `schema-change` skill in `.claude/skills/`. `-e DB_NAME=...` works because `config.Settings` ranks real environment variables above the `.env` file.

Treat `models.py` as the single source of truth for the schema.

## Conventions

- Timestamps are stored as `DateTime(timezone=True)`. The frontend attaches `America/Sao_Paulo` on write, and on read localizes naive values to UTC before converting back to São Paulo for display. The ETL does the same conversion in SQL (`AT TIME ZONE 'America/Sao_Paulo'`).
- After any successful mutation the Streamlit pages call `st.cache_data.clear()` then `st.rerun()` — the `get_data` helpers are `@st.cache_data` and take the token as an argument so the cache keys on the session. A message shown before `st.rerun()` never appears, so the Tracker stashes it in `st.session_state["tracker_toast"]` and shows it as an `st.toast` at the top of the next run.
- Money is typed as text, never `st.number_input`: `frontend/money.py`'s `parse_brl` reads "1.234,56" / "45,9" into a `Decimal` (its `ValueError` message is shown to the person), the page sends it to the API as a string (`str(Decimal)`), and `format_brl` is the only way amounts are displayed ("R$ 1.234,56"; display-only dataframe columns are pre-formatted to text because `NumberColumn` can't put a comma before the cents). Pure helpers live in `money.py` with tests in `frontend/tests/test_money.py`; `entry_preview` mirrors the backend's rounding (installments: all but the last rounded down, as in the ETL's cashflow; shares: `split_logic.split_amount`), so keep them in step if either rule changes. Escape `$` (the page's `md()`) in Markdown elements, where two of them start LaTeX.
- The Tracker's expense entry form is an `@st.fragment`, so typing reruns only the form, not the overview below (not `st.form`: the cascading selects, credit-only installments and live preview must react as you type). Every entry widget key carries `st.session_state["entry_nonce"]`; a successful save bumps it (fresh, empty widgets, date/time reset to now in São Paulo), clears the cache and calls `st.rerun(scope="app")`. `frontend/tests/test_tracker_entry.py` drives it with AppTest and a mocked `requests`.
- Installments only surface in the UI when the selected payment method has `is_credit` true; otherwise `current_installment`/`total_installments` both default to 1. An installment purchase is one row: `price` is the full purchase price and `current_installment` is the installment billed in the month of `transaction_timestamp`, so installment k falls (k − current) months from it (the API rejects current > total). Only the `cashflow` datasource spreads it over months; `/summary/`, `/balances/` and the other datasources count the full price in the purchase month.
- A payment method is a (method, institution) pair, e.g. *Pix · Nubank*. The Tracker's Institution select lists the banks registered for the chosen method plus "N/A" when a row without an institution exists; when "N/A" is the only option it is picked and locked (how Cash works), so a method stored without a bank never blocks the form. Non-cash methods showing only "N/A" get a hint to add the bank in Settings.
- Deletes of dimension rows are expected to fail with a FK violation when records reference them; the endpoints catch that, roll back, and return a 400 with a human-readable message. `GET /categories/` and `GET /payment_methods/` return each row's `expense_count` so the UI can say so up front; `PATCH /categories/{id}` and `PATCH /payment_methods/{id}` edit only the fields sent (renaming relabels past expenses, which point at the row by id), and a create or edit that collides with the unique constraint is a 409 naming the clash.
