# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A household expense tracker: a Svelte web app (`web/`) talks to a FastAPI backend over HTTP, which persists to a Postgres star schema, and an ETL step exports that schema to a Tableau Cloud datasource. Everything runs through `docker-compose.yml` (db, backend, web, backup, pgadmin; the old Streamlit `frontend` is kept for one release behind the `legacy` profile) with `.env` at the repo root supplying every credential.

## Product intent

Two people — the owner and his wife — each log their own expenditures, and the owner analyses them: the current month first, and increasingly month-over-month as history accumulates. Analytics is the point of the project, not a bolt-on, so weigh changes against whether they make the data easier to analyse over time.

Tableau is deliberate scope. The dev site and the embedded dashboard exist because learning Tableau is one of the project's goals, and it stays the long-term home for analysis. The in-app **Overview** (Altair charts over `/analytics/shared`, on Our expenses and My expenses) is an interim view the owner asked for — shared expenses, this month against earlier months — and it lives alongside the **Tableau** page rather than replacing it. Don't grow the Overview into a substitute for Tableau or propose dropping the embed.

The app is organised around two questions: **how are our expenses doing?** (the main one) and **how are my personal expenses doing?** Pages follow them; see Pages below.

This is a learning project. The owner wants to be walked through changes and understand the trade-offs, not handed finished features — default to explaining and proposing sequenced steps, and check before implementing.

**Shared expenses are split by an income-derived proportion, not 50/50.** `FactExpenditure.user_id` is who *paid*; who *bears* the cost lives in `fact_expenditure_split` (one row per person per expense, `share_pct` and `share_amount` snapshotted at write time from `household_setting`). Per-person spending must be computed from the split table, not from `FactExpenditure.user_id`. In Tableau, per-person analysis belongs on the `allocations` datasource; the older `expenditures` datasource still attributes 100% of a shared cost to the payer. The design work lives in the gitignored `notes/` folder, which also holds the project review and roadmap; read `notes/README.md` before proposing schema changes.

## Commands

Docker is the primary workflow. The backend bind-mounts its source and hot-reloads; the `web` service is a built image (nginx serving `web/dist` on 8501 and forwarding `/api/` to the backend), so after editing `web/` run `docker compose up -d --build web`, or develop with `npm run dev` for hot reload. `db`, `backend`, `web` and `backup` have `restart: unless-stopped`, so the app comes back by itself whenever Docker Desktop starts (after a reboot or a crash); `docker compose stop` still stops them for good, and pgAdmin stays manual. It's reached from phones over Tailscale at `http://felipesebben:8501` (the PC's tailnet name), which is also `FRONTEND_BASE_URL`. The legacy Streamlit app: `docker compose --profile legacy up -d frontend`, on :8502.

```powershell
docker compose up --build          # full stack: API :8000, UI :8501, pgAdmin :5050, Postgres on $DB_PORT
docker compose up -d db            # database only (e.g. to run backend locally)
docker compose logs -f backend     # tail one service
docker compose down -v             # DESTROY the postgres_data volume (Alembic rebuilds it on next start)
docker compose build --no-cache backend   # needed after editing pyproject.toml/poetry.lock
```

Running a service outside Docker (the backend from `backend/` with its Poetry project and `.venv`; the web app from `web/` with npm):

```powershell
poetry install
poetry run uvicorn main:app --reload      # backend/ — imports are flat ("import models"), so cwd MUST be backend/
npm install && npm run dev               # web/ — http://localhost:5173, /api forwarded to localhost:8000 (API_PROXY_TARGET overrides)
```

Note that outside Docker the backend reads `DB_HOST`/`DB_PORT` straight from `.env`, which currently holds the Compose values (`db` / `5432`) — running the API on the host therefore requires setting `DB_HOST=localhost` first. Inside Docker, `docker-compose.yml` overrides them to `db:5432` regardless.

**Backups.** The `backup` service (the postgres image's `pg_dump`, an inline loop in `docker-compose.yml`, so no script file with Windows line endings is mounted) checks every `BACKUP_CHECK_SECONDS` (15 min) and writes a compressed dump when the newest one in `BACKUP_DIR` (default `./backups`, gitignored) is `BACKUP_EVERY_SECONDS` (a day) old, going by the file's date, as `home_finances_<YYYY-MM-DD_HHMM>.dump` in São Paulo time. It's built that way because one long sleep failed silently: after a reboot Docker restarts the service before the database accepts connections (`depends_on` only applies to `up`), and a sleeping PC stretches a sleep, so it now waits for `pg_isready` and a missed or failed dump is retried at the next check. After a dump succeeds (never otherwise) it deletes dumps older than `BACKUP_KEEP_DAYS` (14) but always keeps the newest `BACKUP_KEEP_MIN` (7). The copy off the PC is Google Drive for desktop syncing `./backups` (My Computer), not `BACKUP_DIR` on the G: drive, which can mount after Docker starts. `docker compose logs backup` shows each attempt. To restore (this replaces the live data; stop the backend first):

```bash
docker compose stop backend
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner' < backups/home_finances_<date>.dump
docker compose start backend
```

To check a dump without touching the live data, restore it into a scratch database (`CREATE DATABASE restore_check;`, `pg_restore ... -d restore_check`, compare row counts, `DROP DATABASE restore_check;`).

Utility scripts:

```powershell
poetry run python init_db.py              # backend/ — CREATE DATABASE if absent; tables come from Alembic
poetry run python -m etl.main             # backend/ — run the Tableau ETL directly (same code path as POST /refresh)
poetry run python seed.py                 # backend/ — seed months of demo history (--months, --random-seed, --append)
docker compose exec backend python reset_password.py someone@example.com   # set a password by hand (prompts twice)
```

Migrations run inside the backend container, where `DB_HOST=db` resolves:

```powershell
docker compose exec backend alembic current                      # which revision the DB is on
docker compose exec backend alembic history                      # the revision chain
docker compose exec backend alembic revision --autogenerate -m "what changed"
docker compose exec backend alembic upgrade head                 # apply
docker compose exec backend alembic downgrade -1                 # step back one
```

Tests (pytest, in `backend/tests/`) run inside the backend container:

```powershell
docker compose exec backend pytest                                   # whole suite
docker compose exec backend pytest tests/test_split_logic.py -v      # one file
```

Web tests (vitest, `*.test.ts` beside the module in `web/src/lib/`) need no database or API: every pure helper (money, dates, filtering, targets, and the shaping behind each view: `lib/daily/`, `lib/overview/`, `recap.ts`, `briefing.ts`, `joint.ts`, `settle.ts`, `settings.ts`, `entries.ts`, `entryChecks.ts`, `entryPayload.ts`, `shares.ts`). Run them with `cd web && npm test` (one file: `npx vitest run src/lib/money.test.ts`), the type check with `npm run check` and the build with `npm run build`; CI runs all three as the `web-tests` job. There are no component tests: keep logic out of `.svelte` files and in a tested `lib/` module, and look at pages with the `screenshot-check` skill. The legacy Streamlit tests (`frontend/tests/`, `frontend-tests` job) still run until `frontend/` is removed.

API tests hit a real Postgres, never SQLite. `tests/conftest.py` points `DB_NAME` at `<DB_NAME>_test` (or `$TEST_DB_NAME`) before anything imports `database`, drops and recreates that database, migrates it with `alembic upgrade head`, truncates every table after each API test, and drops the database at the end. It refuses to run against a name not ending in `_test`. GitHub Actions (`.github/workflows/ci.yml`) runs the same suite against a Postgres service container on every push and PR to `develop`/`main`. Every PR should add tests for what it changes.

There is no linter or formatter configured. Do not invent commands for them.

## Workflow

Branch from `develop` and open pull requests into `develop`; a release is a pull request from `develop` into `main`. Before each commit, stage by path and run `bash .claude/skills/ship-pr/preflight.sh` (branch and base, nothing like `.env` staged, no credential-shaped literals: GitGuardian scans every commit, and a later fix commit doesn't clear it). CI (`.github/workflows/ci.yml`) runs only for pushes and pull requests to `develop`/`main`, so a pull request stacked on another branch gets no test checks until it is retargeted (close and reopen it to trigger CI). The live database holds real data: back up before a migration (the `backup` service, or an extra dump), and never write test rows to it. Project skills in `.claude/skills/`: `schema-change`, `ship-pr`, `gestalt-review`, `screenshot-check` and `dashboard-assessment` (interviews Felipe about the analysis views, one question at a time).

## Architecture

**Configuration.** Every backend setting goes through `backend/config.py`: a pydantic-settings `Settings` built once at import (`from config import settings`), reading environment variables first and then the repo-root `.env`. Required values (DB_*, `SECRET_KEY`) fail at startup with the variable named; Tableau credentials are optional until `settings.require_tableau()` runs at publish time, and SMTP credentials until `settings.require_email()` runs when sending with `EMAIL_BACKEND=smtp`, so tests and CI need neither. Don't add new `os.getenv` calls — add a field to `Settings` and a line to `.env.example`. The ETL reuses `database.engine` rather than building its own connection. The web app has no settings of its own: it calls `/api` on its own origin (`VITE_API_BASE` overrides it at build time).

**Look and feel.** The app is called **Home Finances**. It follows Apple's Human Interface Guidelines (developer.apple.com/design/human-interface-guidelines, charts and charting-data in particular): Geist on every device (loaded from Google Fonts, so the iPhones and the Windows laptops look the same; digits tabular through `font-variant-numeric`, proportional for the big KPI numbers), a grouped grey page with flat white cards, filled borderless controls, iOS segmented controls for tabs and up to four options (capsule chips for more), translucent top and tab bars, and light and dark mode following the device. Its tokens live in `web/src/app.css` (light and dark sets); the chart palette in `web/src/lib/charts/palette.ts` is those tokens as `var(--…)` strings, so charts switch theme too (never put a hex colour in a component). Every colour has one job: green = household and actions, slate = money owed, orange ▲ = spent more, blue ▼ = spent less; never introduce red/green for good/bad, and always pair colour with an arrow or sign (`Message` tones are info/warn/error/ok, where error and warn are orange and ok is blue). Every page starts with `PageHeader` (title + one-sentence purpose); `Lede` is the "what this is for" line (secondary text with an info glyph), `Callout` leads with an answer (who owes whom), `Notices` the orange-tinted block of in-app notices. Analysis views are charts, not tables (a table belongs where rows are managed: Entries, joint entries, recorded payments), built from `Card`s, one question each (the question is its `title`), flat white on the grey page; a row of cards is a `.grid.cols-N` (it stacks on a phone) with a `minHeight` so they line up. A KPI is `Kpi` (small secondary label, the number, then quiet context lines: one short line each in the secondary colour and regular weight, a change always `lib/delta.ts`'s "▼ R$ 1,8 mil (39%) vs October", exact amounts and what's compared in its `help` (i), never a sentence under the number; ▲/▼ lines as [text, tone], `help` as a tap-able (i)). Charts are SVG Svelte components on d3-scale/d3-shape in `web/src/lib/charts/`, each measuring its own width (`bind:clientWidth`), so they redraw at any width: `RankedBars` (the one way to rank: names left in a column only as wide as the longest, the value at the tip, picked bar brand green and the rest lighter, optional grey last-month tick and dark target tick, i.e. a bullet chart, and a dashed reference line), `ChangeBars` (diverging, lines up row for row beside RankedBars), `Columns` (months; the picked month green, a month in progress faded and dashed, never projected; reference lines named at their right end), `LineChart` (running totals; each line named at its end instead of a legend, a hover/tap readout), `SparkBars` and `MonthSpark` (KPI sparkbars), `Calendar` and `Progress` (This month). Shared anatomy, after the HIG: the data most prominent, no frame or background, a quiet axis line, hairline grid with few ticks in familiar steps, y labels inside the plot on the leading edge above their grid line (the chart lines up with the card's text and gets the full width), values labelled directly, the card's subtitle as the chart's summary, the whole plot area as the scrub target (dots on every line and a translucent readout), and marks that grow in when drawn (off under reduced motion). Bars are square where they meet the axis and rounded only at their far end (`palette.barPath`). From Apple's Weather charts: lines are smooth (monotone, so a running total never dips), the series that matters gets a soft gradient under it (`area`), and "now" is a dot with a halo. This month's hero is one full-width card: the question and the number on the left, the calendar as a small widget top right (`Calendar small`), the running total across the full width below. Heights are rows × `BAR_ROW` (+ `X_AXIS`). Picking is a pill row (`Segmented`) or a select beside what it drives; tapping a bar or a calendar day is only a shortcut to the same pick. The `gestalt-review` skill (`.claude/skills/gestalt-review/`) reviews pages against these grouping rules, and the `screenshot-check` skill shows them in a real browser (a build of `web/` on port 8599, logged in with a minted token, screenshot by Playwright in the installed Chrome, desktop and phone width, `--dark` for dark mode); run both on frontend changes. Its reference, a dataviz course PDF in the gitignored `notes/references/`, must never be committed (its licence forbids redistribution).

**Pages.** A hash router (`web/src/lib/router.svelte.ts`: `#/ours/trend` = page `ours`, tab `trend`; tabs live in the URL so a reload or Back keeps them) and `App.svelte` (a top bar on a wide screen, a bottom tab bar on a phone) pick the page from `web/src/pages/`: `Home.svelte` (login, sign-up, password reset, then the briefing and links), `AddExpense.svelte` (only the entry form), `OurExpenses.svelte` (tabs This month = the daily view, Month by month = the Overview with the Household lens, Monthly recap, Joint account when a joint method exists and you're in the household, Settle up), `MyExpenses.svelte` (This month and Over time, both with the My share lens and a Show select in their filter row: Everything I spent (`all`, the default: shared and personal fetched and added together), Personal only (`personal`), My share of shared (`shared`)), `Entries.svelte` (every expense you can see, to audit and fix; see Editing an expense) and `Settings.svelte`. The Tableau embed is parked in `frontend/parked/tableau.py` (Felipe hid it from the menu on 2026-10-23 until he decides what to do with Tableau). Page files only wire sections together: each tab's body is a component in `web/src/sections/` (`Daily.svelte` and `Overview.svelte` take `lens`, `key`, `showView`; `Recap`, `Joint`, `Settle`, `SettleBox`, `Briefing`, `Where` (where the money goes + what's inside a category), and `EntryForm`, the form Add expense and Entries share), with their cards in `sections/daily/`, `sections/overview/`, `sections/settings/`. Logic and text live in pure, tested modules in `web/src/lib/`. Home's briefing (`sections/Briefing.svelte`, sentences from the pure `lib/briefing.ts`) says, for this São Paulo month: the shared total and mine (my share of shared + personal) against "usual" (the average of the three previous full months over the same days, falling back to last month, else no comparison) with the biggest shared category, who owes whom, and what's left in each joint account; a line with nothing to say is left out, balances and joint lines only for household members.

**Request path.** The web app is a pure HTTP client: it calls the API under `/api` on its own origin (Vite's dev proxy, nginx in Docker; `web/nginx.conf` strips the prefix), so there is no CORS. Everything goes through `web/src/lib/session.svelte.ts`: `get(path)` (cached for a minute per path), `post`/`put`/`patch`/`del` (each clears the cache and bumps `session.version`, which every view reads inside its fetching `$effect`, so the page refetches after a write) and `login()`, which posts the OAuth2 form to `/token`. The token and email are kept in `localStorage` (`hf-session`), so reopening the app on a phone within the timeout doesn't ask again. Writes throw `ApiError` (`status`, `detail`, a readable `message`); confirmations go through `showToast()`.

**Auth.** `backend/auth.py` does bcrypt hashing and HS256 JWT minting; `get_current_user` in `backend/main.py` decodes `sub` (the email) and re-fetches `DimUser`. `SECRET_KEY` is required (startup fails without it), and tokens expire after `ACCESS_TOKEN_EXPIRE_MINUTES` (default 60), which works as an **inactivity timeout**: `POST /token/refresh` swaps a still-valid token for a fresh one (an expired one gets the usual 401), and the web app's `keepAlive()` calls it on any request once the token is over `RENEW_AFTER_MS` (5 min) old, so using the app keeps you logged in. Any 401 calls `endSession()`: it forgets the token and the cache, and every route shows Home's login form with one "You were logged out…" message. `test_auth.py` covers the refresh route.

**Every route except signup, login and password reset requires a token.** `POST /users/`, `POST /token`, `POST /password-reset/request` and `POST /password-reset/confirm` are public; everything else depends on `get_current_user`, either as a parameter (when the handler needs the user) or via `dependencies=[Depends(get_current_user)]`. `tests/test_auth.py` keeps `PROTECTED_ROUTES` (each must reject a missing or invalid token) and `PUBLIC_ROUTES`, and `test_every_route_is_classified` fails until a new route is added to one of them.

**Password reset.** `POST /password-reset/request {email}` always answers 202 with the same body, so it never reveals whether an account exists. For a real account (email matched case-insensitively) it marks that user's earlier unused tokens used, stores a new row in `password_reset_token` — only the SHA-256 hex of a `secrets.token_urlsafe(32)` token (`auth.hash_reset_token`), never the token itself — and emails `{FRONTEND_BASE_URL}/?reset_token=<raw>` as a `BackgroundTasks` job. It sends nothing once the user has 3 tokens created in the last hour. `POST /password-reset/confirm {token, new_password}` locks the matching unused, unexpired row (`FOR UPDATE`), sets the new bcrypt hash and marks the token used in one commit; any failure is a 400 "This reset link is invalid or has expired.", and a password under 8 characters is a 422. Existing JWTs stay valid until they expire. `web/src/pages/Home.svelte` shows a "Set a new password" form when the URL carries `?reset_token=` (the link's shape is unchanged), and a "Forgot password?" fold-out under the login form. Email goes through `backend/email_sender.py`: the `get_email_sender` dependency returns `ConsoleSender` (prints the message, the default, used in dev/tests/CI) or `SmtpSender` (STARTTLS, Gmail by default) per `EMAIL_BACKEND`; tests override the dependency with a recording fake, and `conftest.py` forces `EMAIL_BACKEND=console`. Settings: `EMAIL_BACKEND`, `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`, `EMAIL_FROM`, `FRONTEND_BASE_URL` (the LAN address, so links work from a phone), `PASSWORD_RESET_EXPIRE_MINUTES` (default 30). `backend/reset_password.py <email>` is the no-email fallback: it prompts for the password, and its `set_password()` is what the tests call.

**Hardening for LAN use.** The app is meant to be opened from other devices on the home network, so a signed-up account must not be able to harm the household. `POST /users/` checks `settings.signup_allowed(email)`: `ALLOWED_SIGNUP_EMAILS` (comma-separated, lowercased into a set) restricts signup and returns 403 "Sign-up is restricted on this installation" for anyone else; empty means signup is open, which is what tests and CI rely on (`conftest.py` forces it empty). `DELETE /users/{id}` only deletes the caller's own account (403 otherwise; the FK-violation 400 still applies), and Settings offers only "Delete my account". `GET /users/` still lists every account's name and email to any logged-in user — Settings uses it for the Household list; with the allowlist set, every account is a household member anyway. Don't log emails or passwords at login.

**Ownership model.** `POST /expenditures/` deliberately strips `user_id` from the request body (`model_dump(exclude={"user_id"})`) and substitutes `current_user.user_id` — the frontend still sends a dummy `"user_id": 0`. Reads and deletes go through `visible_to(user)` in `main.py`: the user paid it, **or** holds a split row for it. So a shared expense is visible and deletable by both household members, and an account outside the household sees none of the household's expenses. Use `visible_to` for any new expenditure endpoint.

**Editing an expense.** `PATCH /expenditures/{id}` (`schemas.ExpenditureUpdate`) lets anyone who can see an expense (`visible_to`, as for delete) change it; only the fields sent change, and the payer (`user_id`) never does. The result must pass the rules of a new expense (installment within total, a treat only when shared, a pet only on a `for_pets` category; moving to another category drops the pet), else 422/400. The split is rewritten in the same commit through `ledger.replace_splits`: `is_shared` false makes it personal, `shares` sets a manual split, `reset_split` true re-splits by today's household ratio, and otherwise a shared expense keeps the `share_pct` it was logged with (a new price is split by that same ratio) while one turned shared takes today's ratio. Every edit that changes something stamps `updated_at` and `updated_by_user_id` (migration `a75478837bac`; NULL = never edited, and deleting the editor's account sets it NULL); an edit that changes nothing leaves no trace. There is no duplicate check on an edit. `ExpenditureRead` carries `splits`, `current_installment`/`total_installments`, `updated_at` and `updated_by`. Tests: `tests/test_edit_expenditure.py`. The **Entries** page (`web/src/pages/Entries.svelte`, shaping in the pure `web/src/lib/entries.ts`) lists them with filters (month, Show, logged by, categories, search) and a "Last edit" column, as a table on a wide screen and compact cards on a phone; picking a row opens the same form as Add expense filled in (`EntryForm` with `expense`), with the trace ("Last edited by … on …"), Save changes (PATCH, only the fields that changed) and Delete (after a confirm). Tests: `web/src/lib/entries.test.ts`, `entryPayload.test.ts`.

**Duplicate check.** `POST /expenditures/` first runs `possible_duplicates()`: expenses the caller can see (`visible_to`) on the same São Paulo *day* (the time is ignored, since a backfilled expense gets whatever time it was typed), at the same price and in the same category, that are either logged by the caller with every other field equal too (payment method, nature, installments, pet, shared or not, `is_treat`; a custom split ratio isn't compared), or a shared expense logged by someone else when the new one is shared (the partner logged the same bill, maybe on their own card). Any match is a 409 whose `detail` is `{message, duplicates: [{expenditure_id, logged_by, logged_by_me, transaction_timestamp, price, category, payment_method}]}`; resending with `allow_duplicate: true` saves it. Add expense shows the matches (sentences from the pure `web/src/lib/entryChecks.ts`) with **Save anyway** / **Don't save** in place of Submit, and, to see where backfilling stopped, two captions (`backfillLines`): the earliest and latest shared expense, each saying who logged it, and the earliest and latest of your own personal expenses, each with counts per month. Tests: `tests/test_duplicates.py`, `web/src/lib/entries.test.ts`.

**"Shared" is derived, not stored.** `FactExpenditure.has_other_share` (a `column_property` in `models.py`) is true when someone other than the payer holds a split row; `/summary/`, `ExpenditureRead.is_shared` and the ETL's `is_shared` column all read it. The request field `is_shared` on `POST /expenditures/` now only means "split this by the household ratio". There is no `is_shared` column: migration `bc61f597d8fe` dropped it (its downgrade rebuilds the column from the split rows, covered by `tests/test_migrations.py`), and `POST /expenditures/` excludes the field from the row it writes.

**Star schema.** `backend/models.py` defines `DimUser`, `DimCategory` (unique on primary+sub), `DimPaymentMethod` (unique on method+institution), `DimPet` (unique name), and `FactExpenditure`. `schemas.py` mirrors them for Pydantic; `ExpenditureRead` nests the dimension objects (`pet` may be null), which is why the read query loads them up front (`EXPENDITURE_READ_LOADS` in `main.py`).

**Pets.** `DimCategory.for_pets` marks categories whose expenses are for the pets; `FactExpenditure.pet_id` (nullable) says which one, and NULL on a `for_pets` category means all of them ("Both": one expense, never split per pet). `POST /expenditures/` rejects a `pet_id` on any other category or an unknown pet (400). `/pets/` has GET (with `expense_count`), POST, PATCH (rename) and DELETE (400 while in use). Add expense shows a "Which pet?" radio (each pet plus Both) only for a `for_pets` category — required when there are two or more pets, implicit with one. Every expense datasource in the ETL carries `pet`: the name, `'Both'`, or NULL when the category isn't for pets, so Tableau sums cost per pet across categories.

**Splits and balances.** `POST /expenditures/` writes the expenditure and its split rows in one transaction through `ledger.add_expenditure` (which flushes but never commits, and is also what `seed.py` uses), splitting with the pure `split_logic.split_amount` (last share absorbs the rounding remainder, so parts always sum to the price). An optional `shares` list on the request overrides the household ratio for that one expense (`split_source="manual"`): it must sum to 1, name each person once, only accompany `is_shared` true, and name only household members (a 400 otherwise). A shared expense whose payer has no household share is a 400 too (`ledger.PayerNotInHousehold`), because the ratio would hand all of it to other people. Add expense exposes it as "Custom split for this expense" (you first); there and in Settings' Household, changing one share sets the other person's to the rest (pure `fillRest` in `web/src/lib/shares.ts`, and a copy in `lib/settings.ts` for Settings). `GET /balances/?month=YYYY-MM` reports paid / borne / net per person and the settling transfers (pure `split_logic.settle`). It counts only expenses with a split row for someone other than the payer, so one person's personal spending never appears in the other's view; months are São Paulo calendar months.

**Joint accounts.** `DimPaymentMethod.is_joint` marks an account both people top up in advance (e.g. a shared Nubank debit card for groceries). An expense paid from it is still shared and split as usual, so every "borne"/"my share" figure counts it, but `/balances/` treats each person as having paid exactly their own share, so it nets to zero and never makes anyone owe. Flipping the flag re-reads past expenses on that method. Add expense locks "Shared" on (with a note) for a joint method, Settings has a Joint tick box, and every expense datasource carries `paid_from_joint`. 

**"It's on me".** `FactExpenditure.is_treat` marks a shared expense the payer treated ("don't worry, it's on me"). It is split by the ratio like any other, so it counts in Our expenses and in each person's share, but `/balances/` handles it exactly like a joint-account expense: each person counts as having paid their own share, so it never makes anyone owe. Only a shared expense can be a treat (422 otherwise). Add expense offers an "It's on me" tick box under Shared (not for a joint method, which already never owes), Entries shows "Shared · treat", and every expense datasource carries `is_treat`.

**Joint account pot.** `fact_joint_entry` records what goes into a joint account: `kind` 'deposit' (money in) or 'balance' (what the bank showed then: the starting balance, or a correction when unlogged spending made the app drift). Who deposited is deliberately not stored, and entries never touch `/balances/`. `GET /joint/status` returns, per joint method: `balance` = latest balance check + deposits after it − everything that method paid after it (without a check, counted from the first deposit; NULL until either exists). An expense counts from when the money left: the earlier of its date and `FactExpenditure.created_at` (when it was logged, stamped by `POST /expenditures/`; migration `8cf90e438df9`, NULL on older rows), because bills paid early are dated on their due date. It also returns this São Paulo month's pace: cumulative spend by day against the "usual" month, the average of up to the last 3 *full* months (a month counts only if the account was already tracked — first expense or entry — on its 1st; none yet means `usual_to_day` NULL, "not enough history"), and `runs_out_on` = today + balance ÷ this month's daily rate. Arithmetic lives in the pure `backend/joint_logic.py`. `/joint/entries` has POST, GET (newest first) and DELETE; all four routes are for household members only (403 otherwise), and entries need an `is_joint` method (400). Our expenses gets a **Joint account** tab (only when a joint method exists and you're in the household): three KPI cards, a cumulative `LineChart` in a card (this month solid green with a dot at today, usual dashed grey, each named at its end), a form for deposits/balance checks and recent entries; text and series come from the pure `web/src/lib/joint.ts` (tests beside it).

**Settle up and the monthly recap.** `sections/SettleBox.svelte` (`period`, `key`) leads with who owes whom and, for each debt, the action in the viewer's own words (`lib/settle.ts` `actionLabels`: the one who owes sees "I paid Felipe R$ 447,53", the one owed "Lívia paid me R$ 447,53"): one button records the whole amount as paid today, and a field with a second button records a different amount; anything else (other direction, another day, a note) is in a fold-out below. The **Monthly recap** tab (`sections/Recap.svelte`, sentences from the pure `lib/recap.ts`) is the month you review together, last month by default: the shared total against last month and the usual month (only against months logged in full), what drove it (day-to-day vs fixed, the three biggest moves), each target over or within, then the settle box. Tests: `lib/recap.test.ts`, `lib/settle.test.ts`.

**Settlements.** `fact_settlement` records money moved between members to square up (`/settlements/` POST, GET, DELETE; only the payer or payee may record or delete one). `/balances/` folds them in: net = paid − borne + settled_out − settled_in. A settlement's `period_month` (the month it squares up, set from Settle up's selected period) is deliberately separate from `settled_at` (when the money moved), because October is usually paid back in November; month views filter on `period_month`, and a settlement with `period_month` NULL counts only towards the all-time balance. The ETL publishes them as the `settlements` datasource.

Keep arithmetic in `split_logic.py`, free of DB access, so it stays unit-testable.

**Monthly summary.** `GET /summary/?month=YYYY-MM` (defaults to the current São Paulo month) is from the logged-in user's point of view: their total borne (share of shared + personal) against the previous month, the household's shared total, and their spending by primary category and cost type. It deliberately never exposes the other person's personal spending; cross-person analysis belongs in Tableau. No page reads it any more (My expenses' This month is the daily view now); Settle up on Our expenses reads `/balances/`.

**Shared-expense analytics.** `GET /analytics/shared?month=YYYY-MM&months=N` (month defaults to the current São Paulo month; `months` 1–24, default 12, the window *ends* at `month`) feeds the in-app Analytics Overview. It returns `{month, months, is_partial, as_of_day, rows, first_date}` (`first_date`: the São Paulo day of the first expense in scope ever, so the client knows when logging began): `months` is the whole window oldest first (empty months have no rows, so clients zero-fill from it), and each row is one São Paulo month × primary/sub category × cost type × `nature` (so one-offs can be filtered out) with `household` (sum of full prices), `mine` (sum of the caller's `share_amount`), `count`, and `household_to_day` / `mine_to_day` — the same sums over days 1..`as_of_day` only. `as_of_day` is today's São Paulo day when `month` is the current month (`is_partial` true), else that month's length, so a month in progress can be compared with the same days of earlier months. `GET /analytics/shared/expenses?month=YYYY-MM&primary_category=...` lists the individual expenses behind it (newest first; price, my share and share_pct, payer name, payment method, installments, nature). Both use one privacy rule: the expense is shared (`has_other_share`) **and** the caller holds a split row for it or paid it (the same people `visible_to` admits) — the caller's split row is outer-joined to supply "mine", which is 0 for an expense the caller paid but split entirely onto the partner. Personal expenses (anyone's) never appear, and an account outside the household gets empty rows. Missing categories show as "Uncategorised"/"Unknown", as in `/summary/`. Money is serialised as decimal strings. `basis` (both monthly routes, shared and personal) says how an installment purchase counts: `bought` (the default) in full in its purchase month, `billed` one part per installment in its billing month (`installment_terms()`: a lateral `generate_series`, parts split like the ETL's cashflow, `count` = distinct expenses), so the in-app view can answer both "what did we decide to spend" and "what left the account". Tests: `tests/test_analytics_billed.py`. The code is the last section of `main.py`; tests are in `tests/test_analytics.py`, which freezes "today" by monkeypatching `main.datetime`.

**Personal-expense analytics.** `GET /analytics/personal` and `GET /analytics/personal/expenses` return the same shapes as their `/analytics/shared` twins, for the caller's personal expenses only: ones they paid that nobody else holds a share of (`personal_to(user)`: `user_id` is theirs and not `has_other_share`). A partner's personal spending and every shared expense are excluded. A personal expense is borne in full, so `household` = `mine` = price (and `share_pct` 1 in the expense list). Tests: `tests/test_personal_analytics.py`.

**ETL.** `POST /refresh` calls `etl.main.run_pipeline()` synchronously inside the request: SQL joins → pandas → `pantab` writes one Hyper file per datasource under `artifacts/` (relative to cwd, i.e. `backend/artifacts/` in the container) → `etl/tableau_manager.py` signs in with a Personal Access Token and publishes each with `Overwrite` into `settings.tableau_project_name` (`TABLEAU_PROJECT_NAME`, default `"Finance App 2026"`) — a wrong value silently publishes into another project, leaving the workbook stale. The Tableau datasource name comes from the file name:

- Every expense datasource (`expenditures`, `allocations`, `cashflow`) has `paid_from_joint`: true when the joint account paid, so `paid_by` is only who logged it.
- `expenditures` — one row per expense, `price` attributed to the payer. Kept unchanged so existing workbooks keep working.
- `allocations` — one row per person per expense from `fact_expenditure_split`: `borne_by`, `paid_by`, `share_pct`, `share_amount`, `split_source`, `month_start` (São Paulo), plus category/payment/installment columns. Per-person analysis should `SUM(share_amount)` here. `expense_total` repeats the full price on every row of an expense, so never sum it.
- `cashflow` — the allocation grain spread over installment billing months, built with `generate_series` in SQL: one row per person per expense per installment, with `billing_month`, `purchase_month`, `installment_number`, `total_installments` and `amount`. `SUM(amount)` by `billing_month` is what each month actually cost, card statements included. Each share is divided by the installment count, all but the last rounded *down* to the cent and the last taking the remainder, so parts sum exactly and never go negative. Expenses without installments appear once, in their own month.
- `settlements` — one row per payment between members: `settled_at`, `settled_month_start`, `period_month` (the month it squares up; NULL = all-time), `from_name`, `to_name`, `amount`, `note`, `recorded_by`. Kept out of the spending grain because it moves money rather than spending it.

- `joint_account` — one row per joint-account entry (`kind` deposit/balance, `amount`, `entry_at`, `entry_date`, `month_start`, method/institution, `note`). Its spending side is the expense datasources' `paid_from_joint` rows.

- `calendar` — one row per São Paulo day with no gaps (`date`, `week_start` (Monday), `iso_year`, `iso_week`, `month_start`, `month_number`, `month_name`, `quarter`, `year`, `day_of_month`, `weekday_number` (ISO, Monday = 1), `weekday_name`, `is_weekend`, `is_future`), from 1 January of the first expense's (or settlement's) year to 31 December of the later of this year and the last installment's billing year. Built by `generate_series` at publish time, not stored in Postgres. In Tableau it is the left side: relate `calendar.date` to `transaction_date` (on `expenditures`, `allocations`, `cashflow`) or `settled_date` (`settlements`), or `calendar.month_start` to `cashflow.billing_month`, so days without spending still appear (`ZN()` for zeros).

Every date column is published as TIMESTAMP (pinned with `pd.to_datetime`), so both sides of a relationship have the same type. A datasource with no rows is skipped rather than published empty; the calendar is never empty.

`generate_hyper_file` casts all-NULL *untyped* columns to text, because Hyper rejects a column whose type can't be inferred. Date columns that may be entirely NULL must be pinned with `pd.to_datetime` in their extract, or they publish as text and flip type on a later refresh, which breaks workbooks. The Tableau page iframes a hardcoded Tableau Cloud URL. A publish failure re-raises so the endpoint returns 500.

## Schema changes

**Alembic owns the schema.** Migrations live in `backend/alembic/versions/`, and the backend container runs `alembic upgrade head` before starting uvicorn (the `command:` override on the `backend` service in `docker-compose.yml`), so a fresh volume migrates itself on `docker compose up`. There is no `create_all` call any more — do not add one back, or two systems create the same tables and `alembic_version` stops describing reality.

`alembic/env.py` sets `sqlalchemy.url` from `database.DATABASE_URL` rather than from `alembic.ini`, which keeps credentials out of a committed file; it imports `models` purely so `Base.metadata` is populated; and it sets `compare_type=True` so column type changes are detected at all.

To change the schema: edit `models.py`, autogenerate a revision, **read the generated file before running it**, then upgrade. Autogenerate is a diffing tool, not an oracle — it reads a rename as drop-then-add, and `default=` in `models.py` is a Python-side default that never reaches Postgres, so new columns arrive as NULL on existing rows unless the migration backfills them explicitly.

The first revision (`b24c43f3c0f3`, "baseline: existing schema") was **stamped, not executed**, on the existing database. It describes the pre-Alembic schema — including `price` as `Float`, which the next revision converts to `Numeric(10, 2)`. Because it never ran locally, bugs in it are invisible here. Validate any change to it by building a throwaway database from scratch:

```powershell
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "CREATE DATABASE fresh_check;"'
docker compose exec -e DB_NAME=fresh_check backend alembic upgrade head
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" --schema-only --no-owner fresh_check'
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "DROP DATABASE fresh_check;"'
```

The dumped schema must match the live database. The full procedure — including the review checklist for generated revisions and a `diff` that ignores `pg_dump`'s random `\restrict` keys — is the `schema-change` skill in `.claude/skills/`. `-e DB_NAME=...` works because `config.Settings` ranks real environment variables above the `.env` file.

Treat `models.py` as the single source of truth for the schema.

## Conventions

- Timestamps are stored as `DateTime(timezone=True)`. The frontend attaches `America/Sao_Paulo` on write, and on read localizes naive values to UTC before converting back to São Paulo for display. The ETL does the same conversion in SQL (`AT TIME ZONE 'America/Sao_Paulo'`).
- After any successful write the API helpers clear the GET cache and bump `session.version`, which the views read inside their fetching `$effect`, so everything on screen refetches; the page then confirms with `showToast(...)`.
- Money is integer cents end to end in the web app and typed as text, never a number input: `web/src/lib/money.ts`'s `parseBrl` reads "1.234,56" / "45,9" into cents (its Error message is shown to the person), `toApi(cents)` writes the API's decimal string, `cents()` reads the API's strings back, and `formatBrl` is the only way amounts are displayed ("R$ 1.234,56"; `shortBrl` for chart labels: "R$ 4,1 mil"). `entryPreview` mirrors the backend's rounding (installments: all but the last rounded down, as in the ETL's cashflow; shares: `split_logic.split_amount`), so keep them in step if either rule changes. Tests: `web/src/lib/money.test.ts`.
- Add expense opens with a "Log again" pill row of my last six different expenses (`lib/entries.ts` `recentTemplates`, different = what · how paid · shared or "just me"): picking one fills the form in from it (the same prefill as an edit), dated now and with no price, saved as a new expense.
- The entry form (`web/src/sections/EntryForm.svelte`, shared by Add expense and Entries) reacts as you type: cascading selects, credit-only installments, the pets picker, the joint lock and the live preview. Its request bodies are built by the pure `lib/entryPayload.ts` (an edit sends only what changed, and nothing at all when nothing did; tests in `entryPayload.test.ts`). A successful save shows a toast and resets the form to fresh, empty fields dated now in São Paulo.
- Installments only surface in the UI when the selected payment method has `is_credit` true; otherwise `current_installment`/`total_installments` both default to 1. An installment purchase is one row: `price` is the full purchase price and `current_installment` is the installment billed in the month of `transaction_timestamp`, so installment k falls (k − current) months from it (the API rejects current > total). Only the `cashflow` datasource spreads it over months; `/summary/`, `/balances/` and the other datasources count the full price in the purchase month.
- A payment method is a (method, institution) pair, e.g. *Pix · Nubank*. The Institution select on Add expense lists the banks registered for the chosen method plus "N/A" when a row without an institution exists; when "N/A" is the only option it is picked and locked (how Cash works), so a method stored without a bank never blocks the form. Non-cash methods showing only "N/A" get a hint to add the bank in Settings.
- Deletes of dimension rows are expected to fail with a FK violation when records reference them; the endpoints catch that, roll back, and return a 400 with a human-readable message. `GET /categories/` and `GET /payment_methods/` return each row's `expense_count` so the UI can say so up front; `PATCH /categories/{id}` and `PATCH /payment_methods/{id}` edit only the fields sent (renaming relabels past expenses, which point at the row by id), and a create or edit that collides with the unique constraint is a 409 naming the clash.
