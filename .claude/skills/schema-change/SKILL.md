# Changing the schema

Alembic owns the schema; `backend/models.py` is the source of truth for what it should be. Never call `Base.metadata.create_all`, never edit the database by hand in pgAdmin, and never edit a revision that has already been merged — write a new one.

Follow the steps in order. Each step ends with a check; do not move on until it passes.

## 0. Before touching code

- Read `notes/README.md` (gitignored design notes) and whatever it points to for the area you're changing. Schema decisions there — e.g. splits snapshotting `share_pct`/`share_amount` at write time — are deliberate.
- Ask: does this change make the data easier to analyse month over month? Analytics is the point of the project.
- Confirm the stack is up and the DB is at head:

  ```bash
  docker compose exec backend alembic current
  ```

  Expected: one revision id followed by `(head)`. If it isn't at head, stop and find out why before generating anything — autogenerating against a stale DB produces a revision that re-does old work.

## 1. Edit `backend/models.py`

Make the model change. Watch for:

- **`default=` is Python-side only.** It never reaches Postgres. If existing rows need a value, use `server_default=` and/or backfill in the migration (step 3).
- **Money is `Numeric(10, 2)`**, never `Float` (see revision `7a027ff4174f`).
- **Timestamps are `DateTime(timezone=True)`.**
- **Name constraints explicitly** (`CheckConstraint(..., name="ck_...")`, as `fact_settlement` does) so a later migration can drop them by name.
- Update `backend/schemas.py` if the API should expose the change.

## 2. Autogenerate the revision

```bash
docker compose exec backend alembic revision --autogenerate -m "short imperative description"
```

Check: the output prints `Generating .../alembic/versions/<id>_<slug>.py`. If it says nothing was detected, the model change didn't register (typo, model not imported) — fix that rather than writing an empty revision.

## 3. Read the generated file — this is the step that matters

Autogenerate is a diffing tool, not an oracle. Open the file and check each item:

| Look for | Why it's wrong | Fix |
|---|---|---|
| `drop_column` + `add_column` on the same table | Alembic reads a **rename** as drop-then-add, which **destroys the data** | Replace with `op.alter_column(table, old, new_column_name=new)` |
| `add_column(..., nullable=False)` with no `server_default` | Fails on any table that already has rows | Add as nullable → `op.execute("UPDATE ...")` backfill → `alter_column(nullable=False)` |
| New column that existing rows need a value for | Arrives as NULL; `default=` in models.py doesn't help | Backfill explicitly with `op.execute(...)` |
| Type change (`alter_column(type_=...)`) | Postgres may need `postgresql_using="col::newtype"` for non-trivial casts | Add the `USING` clause; think about rounding/truncation |
| Change you expected but don't see | Autogenerate misses some things — e.g. FK `ondelete` changes, server defaults, check constraints | Write the ops by hand (revision `76b94fdde540` is a hand-written FK change) |
| Changes you *didn't* make | The live DB has drifted from models.py | Stop. Investigate before migrating |
| `downgrade()` | Must exactly reverse `upgrade()`, in reverse order | Fix it; a backfill's downgrade may be a no-op, say so in a comment |

Remove the `# ### commands auto generated by Alembic - please adjust! ###` markers once you've edited the body, so it's clear the file was reviewed.

## 4. Apply it, and prove it reverses

```bash
docker compose exec backend alembic upgrade head
docker compose exec backend alembic downgrade -1
docker compose exec backend alembic upgrade head
docker compose exec backend alembic current
```

Expected: no errors, and the last command prints the new revision id with `(head)`. The round trip proves `downgrade()` works while it's cheap to fix.

## 5. Prove a fresh database builds the same schema

The live DB started from a *stamped* baseline (`b24c43f3c0f3` never ran locally), so it can differ from what the migration chain produces from scratch. Build a throwaway DB and diff the two:

```bash
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "CREATE DATABASE fresh_check;"'
docker compose exec -e DB_NAME=fresh_check backend alembic upgrade head
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" --schema-only --no-owner "$POSTGRES_DB"' > /tmp/live.sql
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" --schema-only --no-owner fresh_check' > /tmp/fresh.sql
diff -I 'restrict [A-Za-z0-9]*$' /tmp/live.sql /tmp/fresh.sql && echo "SCHEMAS MATCH"
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "DROP DATABASE fresh_check;"'
```

Expected: `SCHEMAS MATCH`. The `-I` filter is required: recent `pg_dump` wraps every dump in `\restrict <random key>` / `\unrestrict <random key>` lines, so an unfiltered diff never matches. Always run the `DROP DATABASE` line, even if the diff fails. Any difference means the chain and the live DB disagree — fix the migration, don't hand-patch the live DB.

`-e DB_NAME=fresh_check` works because `config.Settings` ranks real environment variables above `.env`.

## 6. Tests

The test suite builds its database with `alembic upgrade head` from scratch, so running it also exercises the migration chain:

```bash
docker compose exec backend pytest
```

Expected: all tests pass. Add tests for what the change enables — a new column should show up in an API test that writes and reads it; a new constraint should have a test that violates it and gets the expected error. If the column carries arithmetic, keep that logic in `split_logic.py` and unit-test it there.

## 7. Follow-through

- **ETL:** if the column matters for analysis, does `backend/etl/main.py` need to export it to the `expenditures` or `allocations` Hyper file? A column only Postgres knows about is invisible in Tableau.
- **CLAUDE.md:** update the Architecture / Star schema section if the change alters the model described there.
- **Commit** the model change, the revision file, and its tests together, so the branch never has a model without its migration.
